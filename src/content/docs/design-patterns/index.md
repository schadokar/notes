Design patterns are proven solutions to recurring design problems. They give teams a shared vocabulary and reduce the cost of change by capturing intent, not just code.

## Categories

- **[Creational](/design-patterns/creational/singleton)** — how objects get built: Singleton, Factory Method, Abstract Factory, Builder, Prototype.
- **[Structural](/design-patterns/structural/adapter)** — how objects compose: Adapter, Bridge, Composite, Decorator, Facade, Proxy.
- **[Behavioral](/design-patterns/behavioral/strategy-pattern)** — how objects interact: Strategy, Observer, Command, State, Template Method, Chain of Responsibility, Iterator.
- **[Distributed](/design-patterns/distributed/circuit-breaker)** — patterns for systems across the network: Circuit Breaker, Saga, CQRS, Event Sourcing, Outbox, Sidecar, Bulkhead, Retry with Backoff, Strangler Fig, Repository.

## How to use these notes

Each pattern is written as a short, opinionated reference: the problem it solves, when it actually pays off, when it doesn't, and a minimal example. Patterns are tools, not goals — reach for them when the shape of the problem matches, not because the name sounds good in a design doc.
